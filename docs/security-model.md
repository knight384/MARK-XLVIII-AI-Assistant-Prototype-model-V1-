# Security Model

This document describes JARVIS's threat model as of Phase 6, and is
intentionally specific about what is and isn't protected. **This is not a
claim that the system is fully secure or production-safe.** It is a
description of the actual boundaries in place, so anyone extending or
deploying this system knows what to rely on and what not to.

## Trust boundaries

```
Trusted:
  - The user operating the local desktop app
  - Code in actions/*.py, core/*.py (reviewed, checked into the repo)
  - Tool/agent risk metadata (developer-declared, not model-declared)

Untrusted:
  - Content generated by the Gemini model (tool-call arguments, generated
    code for desktop_control's "task" action, dev_agent's planned files
    and run commands)
  - Anything arriving via the dashboard (remote network requests)
  - Uploaded files processed by file_processor
  - Web content fetched by web_search/browser_control
```

The core rule: **the model can propose, but the Policy Engine decides
whether execution is permitted, and untrusted code executes only inside an
explicit isolation boundary when one applies.**

## Model-generated code

Two distinct paths, with two distinct outcomes, and the difference is
deliberate (see `docs/sandbox.md`'s "what is NOT sandboxed" section):

- **`dev_agent`'s planned run commands** — general-purpose (no host GUI
  dependency) → routed through `SandboxManager` (Docker when available;
  the host-restricted fallback otherwise; refused outright for CRITICAL
  risk with no sandbox). Additionally gated by mandatory CRITICAL-risk
  policy approval on every call.
- **`desktop_control`'s "task" action** — generates code that directly
  controls the host GUI (mouse, keyboard, windows) → cannot be
  containerized without breaking the feature. Protected instead by
  mandatory CRITICAL-risk policy approval showing the generated task
  description to the user before every execution, plus a restricted-
  builtins `exec()` as defense-in-depth (explicitly **not** treated as the
  actual security boundary — the approval gate is).

## Tools and risk classification

Every tool declares `ToolMetadata.risk_level` (Phase 3) and every call now
passes through `PolicyEngine.evaluate()` (Phase 6) before executing. See
`docs/tools.md` for the full per-tool risk table and `docs/architecture/
security-and-policy.md` for how the engine decides.

Notable classifications after Phase 6:

| Tool | Risk | Real isolation? | Actual protection |
|---|---|---|---|
| `dev_agent` | CRITICAL | Yes (SandboxManager, when Docker available) | Sandbox + mandatory approval |
| `desktop_control` | CRITICAL | No (structurally incompatible — host GUI) | Mandatory approval + restricted exec() |
| `browser_control` | HIGH | N/A (not code execution) | Isolated profile by default + mandatory approval |
| `computer_control`, `file_controller`, `code_helper` | HIGH | N/A | Mandatory approval |
| `send_message`, `open_app`, `computer_settings`, `screen_process`, `game_updater`, `shutdown_jarvis`, `file_processor` | MEDIUM | N/A | Policy-configurable, allowed by default |

## Agents

Every `AgentMetadata.max_declared_risk` (Phase 4) is now enforced (Phase
6): an agent can never trigger a tool riskier than its own declared
ceiling, under any policy configuration — this is a hard deny, not subject
to approval or override. See `docs/agents.md` for the per-agent ceiling
table.

## Browser profiles

**Before Phase 6**: `browser_control` tried the user's real, authenticated
browser profile first, falling back to an isolated profile only on
failure — meaning ordinary browser automation had access to existing
logins/sessions by default.

**After Phase 6**: the isolated `~/.jarvis_profiles/<browser>` profile is
used by default. The real authenticated profile requires an explicit
`use_real_profile: true` argument — which is visible in the mandatory HIGH-
risk approval prompt, since `browser_control` requires approval by default
regardless of which profile is used.

## Filesystem

`file_controller`'s read/write/delete/move operations are HIGH risk and
require approval by default. Sandbox workspaces (`SandboxWorkspace`)
refuse path traversal outside themselves and never expose credential
stores, SSH keys, browser profiles, or `.env` files by default.

## Credentials

Unchanged from Phase 1: secrets live in the OS keychain or a gitignored
local file, never in source control, never logged (Phase 1's
`SensitiveDataFilter` plus Phase 6's own heuristic argument redaction in
`ToolExecutor._summarize_args` for approval prompts and audit events).
The host-restricted sandbox fallback additionally strips the inherited
process environment so a sandboxed subprocess doesn't automatically see
the parent process's environment variables.

## Dashboard / remote access

Remote (dashboard) requests are tagged `source=dashboard` in the
`PolicyContext` (see `docs/architecture/security-and-policy.md`'s "known
limitation" section for the precision caveat on multi-tool-call turns) and
receive stricter defaults: CRITICAL denies outright by default, HIGH is
independently configurable from local HIGH. The dashboard has **no
separate "remote allow everything" pathway** — every dashboard-originated
tool call passes through the exact same `PolicyEngine`/`ToolExecutor` as
every local call. Dashboard authentication itself (the pairing-key/token
flow from Phase 1) was not redesigned in Phase 6 — its cryptographic
strength remains unassessed (flagged, unresolved, since the Phase 0
audit).

## Memory

Phase 5's privacy safeguards are unchanged and still apply: secret-shaped
content is refused at write time, memory content is never logged at INFO
level. Phase 6 adds: `PolicyContext.involves_private_memory` exists as a
declared field for a tool/agent to set when relevant, so a future
extension of the policy rules can factor memory sensitivity into a
decision — no rule currently reads it (this is a documented extension
point, not a claim of memory-aware policy today).

## What Phase 6 does NOT claim

- **Not a hardened multi-tenant system.** This remains a trusted,
  single-user, local-first assistant with a remote-control dashboard — not
  a system designed to safely serve mutually-untrusting users.
- **Not "production-secure."** The host-restricted sandbox fallback is
  explicitly weaker than real isolation; Windows resource containment
  without Docker is limited; dashboard authentication strength is
  unassessed.
- **Not immune to a sufficiently capable local attacker** with the same OS
  permissions as the user running JARVIS — this system does not attempt to
  defend against that; it defends against *accidental* or *model-driven*
  dangerous actions being taken without the user's awareness/consent.
- **Docker sandbox testing was NOT VERIFIED** in the development
  environment used to build this phase (no Docker binary present) — see
  `docs/sandbox.md`'s Limitations section.
